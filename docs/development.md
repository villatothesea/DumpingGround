# DumpingGround 开发文档

版本：0.2（以功能验收为当前优先级）  
状态：基本交互重做，按功能验收记录判断完成度  

> 当前执行规则：先完成并实际验证进程查看、选盘、扫描过程、结果联动和取消/重扫，再优化效率。此前构建和启动通过不足以证明可用；以 [acceptance.md](acceptance.md) 的交互测试和本应用截图为准。目标仍是 PE / WizTree 的工作流；未实现的能力不能仅通过改写范围视为完成。
目标平台：Windows 10/11 x64，后续评估 ARM64  
项目名：DumpingGround

## 1. 项目目标

DumpingGround 是一个 Windows 原生轻量系统工具，把两类高频排障能力放在同一个应用中：

1. 进程查看与分析，核心体验对标 Microsoft Sysinternals Process Explorer。
2. 磁盘空间分析，核心体验对标 WizTree：快速扫描目录或磁盘，用 treemap 直观展示空间分布，并支持逐层下钻。

首要产品约束是低磁盘占用和低常驻内存。进程页是默认启动页，必须保持轻量；磁盘扫描只在用户主动进入磁盘页并选择位置后启动，扫描索引不进入常驻进程页。

本项目使用 [MyGo](https://github.com/egoist/mygo) 的 native UI 架构：Go 负责应用和 Windows 数据采集，`github.com/egoist/mygo/ui` 负责原生界面、虚拟化列表、表格、布局、输入和 GPU 绘制。优先复用 MyGo 已有组件；没有现成组件时，使用 MyGo 的自定义 widget / drawing API 实现，并遵守其线程模型、可测试视图模型、跨平台接口边界和 `CGO_ENABLED=0` 约束。

## 2. 产品边界

### 2.1 首版必须具备

进程页：

- 进程树视图：父子层级、展开/折叠、刷新后尽量保持展开状态和选中项。
- PID、进程名、CPU 使用率、内存使用量、内存百分比、I/O 读写、线程数、用户名、完整路径。
- 排序、搜索、列显示/隐藏、自动刷新开关和刷新周期。
- 结束进程、结束进程树；高权限操作需要明确反馈失败原因。
- 进程详情页或详情面板：基本信息、命令行、环境/路径信息、模块列表、线程列表。
- 右键菜单：打开文件位置、复制字段、结束进程、属性。
- 进程采样在后台执行，UI 线程只接收快照，不执行阻塞式系统调用。

磁盘页：

- 选择盘符或目录后扫描。
- 扫描进度、已发现文件数、已扫描大小、取消和重新扫描。
- 目录树/列表与 treemap 联动。
- treemap 按文件/目录占用大小布局，支持点击下钻、返回上级、悬停显示路径和大小。
- 显示逻辑文件大小与实际占用空间的口径说明；首版默认以实际文件大小为主，同时采集可获得的分配空间。
- 排除或安全处理符号链接、目录联接、权限不足、回收站、系统目录和重复遍历。
- 扫描完成后允许清理当前索引，避免磁盘页长期占用内存。

应用基础：

- 单实例运行。
- 深色/浅色主题跟随系统。
- 高 DPI 可用。
- 不依赖 WebView2，不引入 Electron、浏览器内核或常驻外部进程。
- 发布版本裁剪 inspector 和调试能力。

### 2.2 首版明确不做

以下能力属于后续阶段，首版不为了追求“完全复刻”而拖慢可用版本：

- 内核驱动、内核句柄回调、Rootkit/反 Rootkit 能力。
- 跨机器进程查看。
- 完整 WinDbg 级符号解析、线程栈采集和转储分析。
- 全局实时句柄搜索、DLL 反向搜索、锁定文件的强制解锁。
- NTFS MFT 直读已加入实验性路径，权限不足或不支持的元数据布局自动回退；管理员实机验收仍待完成。
- 自动删除文件、自动清理系统文件、注册表清理等高风险动作。
- 把整个扫描索引永久写入磁盘作为默认行为。

## 3. 关键设计决策

### 3.1 UI 技术路线

使用 MyGo native UI，不使用 MyGo web frontend。原因是 native UI 不启动 WebView2，启动更快，内存结构更可控，且 MyGo 已提供虚拟化 list/table/outline、原生输入、GPU 绘制和 headless view test。

窗口采用单主窗口 + 页面导航：

- 顶部工具栏：页面切换、刷新、搜索、设置和状态。
- 左侧窄导航栏：进程、磁盘、设置/关于。
- 内容区：页面自身的表格、树、treemap 和详情面板。
- 底部状态栏：采样状态、扫描状态、权限状态和资源统计。

布局在普通窗口尺寸下优先保证进程树和磁盘 treemap 的可读性；窗口缩窄时，次要列隐藏到详情面板，不让表格产生不可用的横向挤压。

### 3.2 进程数据模型

采集层生成不可变的 `ProcessSnapshot`，UI 层只消费快照。核心结构包括：

- `PID`、`PPID`、进程名、路径、命令行、用户名。
- 创建时间、线程数、句柄数（能安全取得时）。
- 工作集、私有工作集、提交大小。
- CPU 时间增量计算出的 CPU 百分比。
- I/O 读写累计量和采样期间增量。
- 访问权限、是否提升、是否为系统进程等状态。

CPU 和 I/O 使用两次采样的差值计算，不为每次绘制重复读取系统信息。进程退出和 PID 重用通过创建时间或进程对象身份校验处理，不能只依赖 PID。

Windows 数据采集优先级：

1. Toolhelp / PSAPI / NT 系统 API 等不需要额外进程的系统接口。
2. 性能计数器只在需要且可控时使用。
3. WMI、PowerShell 仅作为明确的兼容性后备，不作为刷新主路径。
4. 任何需要管理员权限的功能都延迟到用户主动查看或执行时。

### 3.3 磁盘扫描模型

首版使用后台目录遍历，先保证正确性、可取消和低风险；后续在独立模块中评估 NTFS MFT 扫描。扫描器输出紧凑的扁平节点数组，而不是每个文件都创建带完整路径和多个 Go 指针的对象。

节点最小字段：

- 父节点编号、名称引用、类型、文件大小、分配大小、文件属性。
- 目录的子节点范围或排序索引。
- 错误状态和扫描状态。

完整路径按需从父链拼接；UI 只为当前展开目录建立可见行。扫描过程中使用有界队列和取消信号，避免文件数量异常时无限制堆积。默认不跟随符号链接和目录联接；遇到权限错误记录为不可访问节点，不让整个扫描失败。

treemap 采用可复用矩形缓冲区实现 squarified treemap 或等效的稳定布局算法：

- 当前目录的直接子项按大小降序布局。
- 小于显示阈值的项目合并为“其他”，避免生成大量无意义矩形。
- 矩形只存当前展示层，切换目录后释放或复用缓冲区。
- 命中测试按布局结果执行，不为每个矩形建立重量级 UI 元素。

空间口径：界面同时显示“文件大小”和“占用空间”能取得的值；默认排序和 treemap 使用占用空间，无法取得时回退文件大小。稀疏文件、压缩文件、硬链接、云文件占位符和重解析点需要显示说明或状态。

### 3.4 低资源策略

- 默认刷新周期 1 秒；无变化时只更新必要行。
- 采集、磁盘扫描、详情加载全部在后台 goroutine 执行。
- 进程表使用虚拟化表格，只构建可见行。
- 不保存完整历史曲线；需要曲线时使用固定环形缓冲区。
- 磁盘索引只在磁盘页存在，离开页面或用户点击清理后立即释放。
- 图标和字体资源按需加载并设置上限；首版不读取每个文件图标。
- 磁盘扫描并发度默认受限，避免扫描过程拖垮磁盘和 CPU。
- 最小化或窗口不可见时降低刷新频率；完全空闲时不请求新帧。
- 禁止引入大型图表、文件索引或浏览器运行时依赖。

目标基线：

- 发布 EXE 尽量控制在 20 MB 内，实际以构建结果记录为准。
- 仅进程页稳定私有工作集目标仍为 50 MiB 以内。未达标时记录差距，不以空窗口增量替代原目标；性能优化在功能验收后集中处理。
- 进程页稳定刷新不得持续增长内存。
- 磁盘扫描内存按文件数量增长，但必须提供取消、释放和基准测试；首版不承诺全盘百万级文件的固定内存上限。

## 4. 目录结构

计划采用以下结构，按功能边界拆分，避免把 Windows API 和 UI 混在一起：

```text
DumpingGround/
├── cmd/dumpingground/       # 程序入口
├── internal/app/            # 页面状态、导航、生命周期、配置
├── internal/process/        # 进程采集、快照、CPU/I/O 采样、权限
├── internal/disk/           # 扫描器、紧凑索引、空间统计、取消
├── internal/treemap/        # 与 UI 无关的布局和命中测试算法
├── internal/windows/        # Windows 专属 API 适配
├── internal/ui/             # MyGo native UI 页面和自定义 treemap widget
├── internal/format/         # 字节、时间、百分比、路径等显示格式
├── resources/               # 图标和少量静态资源
├── docs/                    # 开发文档、性能记录、决策记录
├── go.mod
├── go.sum
├── mygo.json
└── README.md
```

`internal/treemap` 和采集层尽量保持平台无关，便于单元测试；Windows API 调用集中在 `internal/windows` 或对应功能包的 `_windows.go` 文件。

## 5. 开发顺序和验收标准

严格按以下顺序推进，每一步完成后运行对应检查并记录结果：

### 阶段 0：项目基线

- 初始化 Go module 和 MyGo native UI 模板。
- 建立目录结构、README、LICENSE 说明和 Git 提交规则。
- 确认 `CGO_ENABLED=0` 能构建 Windows x64。
- 建立最小窗口和应用生命周期。

验收：能启动空窗口，`go test ./...` 和 Windows 交叉编译通过。

### 阶段 1：UI 壳和通用组件

- 完成导航、工具栏、状态栏、主题和响应式布局。
- 复用 MyGo 的 table/list/outline/search/button/menu/dialog 等组件。
- 为进程页和磁盘页留下稳定的状态接口。

验收：页面切换、主题变化、窗口缩放和键盘焦点可用；没有 WebView2 进程。

### 阶段 2：进程采集和进程页

- 实现 Windows 进程枚举和基础快照。
- 实现增量 CPU/I/O 计算、进程树、虚拟化表格、排序和搜索。
- 实现详情面板、按需模块/线程读取。
- 实现结束进程及权限错误反馈。

验收：在普通 Windows 机器上稳定刷新；PID 重用不串数据；进程树展开状态可保持；刷新 10 分钟无内存持续增长。

### 阶段 3：磁盘扫描核心

- 实现可取消、可限速的后台目录扫描。
- 实现紧凑索引、大小汇总、错误节点和链接保护。
- 实现扫描状态、取消、释放和重新扫描。

验收：选择任意普通目录可完成扫描；权限错误可见；取消后 goroutine 退出且索引释放；扫描中 UI 可正常操作。

### 阶段 4：treemap 和磁盘页

- 实现独立的 treemap 布局、命中测试和下钻返回。
- 接入目录列表、排序、搜索和 treemap 联动。
- 增加大项目标签、悬停提示和“其他”聚合。

验收：同一目录数据与列表大小一致；点击任意矩形可定位；窗口缩放布局稳定；百万级模拟节点的布局测试有明确耗时和分配数据。

### 阶段 5：低资源优化和稳定性

- 建立进程页、扫描页、空闲页的 Windows 内存基线。
- 削减非必要资源、分配和刷新。
- 处理高 DPI、暗色模式、权限、系统进程、挂载盘、重解析点和长路径。
- 增加崩溃保护、日志分级和错误提示。

验收：发布构建、测试、资源占用报告完成；核心页面无明显增长；长时间运行和取消扫描通过。

### 阶段 6：发布和后续路线

- 生成 Windows x64 发布包和校验和。
- 写用户 README、已知限制和故障排查。
- 评估 ARM64、MFT 扫描、句柄/DLL 搜索、线程栈和转储能力。
- 对 MyGo 通用能力提出独立、最小化的 PR，而不是把 DumpingGround 的业务代码提交给框架。

## 6. 测试策略

单元测试：

- 字节、时间、百分比和路径格式化。
- 进程快照合并、PID 重用、CPU/I/O 差值。
- 进程树构建和排序。
- treemap 布局面积守恒、稳定性、命中测试、空输入和极端值。
- 扫描器的取消、错误、链接和聚合行为，使用临时目录与模拟文件系统边界。

集成测试：

- Windows 真实进程枚举和权限路径。
- 真实目录扫描、重解析点跳过和取消。
- UI 使用 MyGo `ui.Tester` 做无窗口交互测试。

手工验收：

- Windows 10/11、普通用户/管理员、深色/浅色、100%/150%/200% DPI。
- 空目录、超长路径、中文路径、权限拒绝目录、网络盘、移动盘和云同步目录。
- 进程快速创建/退出、系统进程、权限不足进程和 PID 重用。
- 进程页持续运行 10 分钟；磁盘页扫描后取消、切页、重新扫描。

性能记录统一保存到 `docs/performance.md`，至少记录：构建产物大小、私有工作集、工作集、提交内存、GPU 内存、CPU 占用、扫描速度、扫描峰值内存和页面空闲值。每次优化必须注明机器、系统、Go/MyGo 版本和采样方法。

## 7. 依赖和复用规则

- 首选 MyGo 当前公开 API 和官方 `ui` 组件。
- 只有现有组件无法表达产品交互时才写自定义 widget；自定义组件要有 view test 或算法测试。
- 业务代码不修改 MyGo 源码，不复制 MyGo 内部实现。
- 如果发现 MyGo 缺少通用能力，先在 DumpingGround 中用最小适配验证需求，再单独整理成框架 PR。
- PR 候选必须是通用能力，例如虚拟化表格增强、treemap 通用布局、列表性能、Windows UI 能力或无障碍支持；不得包含项目名、业务字段和产品策略。
- 所有平台无关算法都不得依赖 Windows API，确保可以在开发机上快速测试。

## 8. Git 提交规则

提交消息使用 Conventional Commits：

```text
<type>(<scope>): <imperative summary>
```

允许的 `type`：

- `feat`：新增用户可见能力
- `fix`：修复行为或兼容性问题
- `perf`：性能、内存或体积优化
- `refactor`：不改变行为的结构调整
- `test`：测试变化
- `docs`：文档变化
- `build`：构建、依赖或发布变化
- `chore`：维护性工作

推荐 scope：`app`、`ui`、`process`、`disk`、`treemap`、`windows`、`format`、`docs`、`release`。

规则：

1. 每个提交只完成一个可描述的变化，避免把 UI、采集和大规模格式化混在一起。
2. 提交标题使用英文动词开头，不超过 72 个字符，不加句号。
3. 提交正文说明动机、实现边界、验证命令和已知限制；性能变化附前后数据。
4. 完成功能后再提交，禁止提交无法编译的中间状态。
5. 纯格式化不能掩盖功能变更；格式化单独提交或与同一功能一起保持最小范围。
6. 提交前至少运行受影响包的测试；阶段结束运行 `go test ./...`、`go vet ./...` 和目标构建。
7. 未来向 MyGo 提交 PR 时，一个 PR 只解决一个通用框架问题，提交历史沿用上述规则但不混入 DumpingGround 业务代码。

第一批提交建议：

```text
docs: add DumpingGround development plan
build: initialize native MyGo application
feat(ui): add application shell and navigation
feat(process): add Windows process snapshots
feat(ui): add process tree and details
feat(disk): add cancellable directory scanner
feat(treemap): add size based layout and hit testing
feat(ui): add disk analyzer and treemap view
perf(app): reduce idle memory and refresh work
```

## 9. 风险和决策记录

- MyGo 是较新的框架，发布前必须锁定版本并保存构建信息；不能只依赖浮动的 `@latest`。
- Go 运行时和 MyGo native UI 有固定基础内存，最终资源占用需要以 Windows 实测为准。
- Process Explorer 的句柄/DLL 深度功能与 WizTree 的 MFT 级速度都不是单纯 UI 功能；它们放入后续阶段，避免破坏首版低资源目标。
- 扫描结果必须明确“文件大小”和“实际占用”口径，不能把两者混为一个数字。
- 任何删除动作都默认不自动执行；首版只做分析和打开位置，清理功能必须另行设计确认流程。
